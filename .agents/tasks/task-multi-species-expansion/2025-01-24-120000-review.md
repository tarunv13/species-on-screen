# Multi-species expansion from tiger prototype to 10-species platform

The Eco-Cinema Observatory evolves from a single hardcoded tiger profile into a data-driven multi-species site. A species registry (`src/data/species-registry.js`) serves as the single source of truth for 10 flagship species, feeding both the 3D globe markers and a new gallery on the index page. Individual species profile pages (`species/*.html`) load pre-populated JSON data at runtime via fetch, rendered into glass-panel sections by a dedicated `species-page.js` module. The Vite config dynamically discovers species HTML pages for multi-page build. A CI fix, SEO metadata, accessibility primitives, and a navigation breadcrumb round out the change.

**Watch for:** Taxonomy data in 8 of 10 JSON files is factually wrong (confirmed) — the GBIF fetch script appears to have populated fields from unrelated taxa. The species profile pages inject JSON strings directly into `innerHTML` without sanitization (likely XSS vector if data source ever becomes user-influenced). Species pages render duplicate navigation bars — one static in HTML, one injected by `initNav()` (confirmed).

## High-level view

The species registry is a well-structured central authority that drives both the globe and the gallery. Every globe marker, every gallery card, and every inter-species nav link derives from this single array. The decision to use static pre-fetched JSON rather than runtime API calls is appropriate for a GitHub Pages deployment, though it places a quality burden on the fetch script's output.

The multi-page Vite configuration dynamically resolves all `species/*.html` files into Rollup inputs, which means adding a species requires only a new HTML file and a JSON data file — no build config changes.

The taxonomy data shipped with the commit is largely incorrect. The fetch script's fallback path reads existing files back (a circular pattern), and the GBIF API calls appear to have returned data for the wrong taxon keys or the responses were misattributed. Only `blue-whale.json` and `giant-panda.json` carry plausible taxonomy. The rest show families like Felidae for elephants and Alligatoridae for hawksbill turtles.

The species profile pages use `innerHTML` to render JSON values into the DOM. The JSON files are committed static assets served from the same origin, so the immediate XSS risk is low. However, the fetch script can overwrite these files from API responses, and no sanitization exists in the rendering pipeline — a future supply-chain risk if OMDb or GBIF data ever contains HTML entities or injected markup.

<summary>Issues (5)</summary>

1. **Incorrect taxonomy data in 8/10 JSON files** — The `taxonomy` objects in tiger, snow-leopard, orangutan, hawksbill-turtle, african-elephant, polar-bear, coral-reef, and amazon-river-dolphin JSON files contain completely wrong families, genera, and species names (e.g., elephant listed as Felidae/Panthera onca). Re-run the fetch script with corrected GBIF taxon keys or manually fix the fallback data.
2. **innerHTML injection without sanitization** — `species-page.js` renders JSON string values directly via `innerHTML`. Escape HTML entities before injection, or use `textContent` for plain-text fields and create elements programmatically for structured content.
3. **Circular fallback in fetch script** — `loadFallback()` reads the same file the script is about to overwrite. If the file already contains bad data (as it does now), re-running the script without a working API key perpetuates the error. Add a separate verified fallback data source or validate GBIF responses against the species registry's `scientificName`.
4. **Duplicate nav on species pages** — Each species HTML file includes a static `<nav>` element, and `initNav()` in `species-page.js` prepends a second nav bar via DOM manipulation at runtime. Either remove the static nav from the HTML or skip `initNav()` on species pages.
5. **No error recovery for species gallery** — `species-gallery.js` imports `SPECIES` synchronously and builds cards, but if the registry were empty or malformed, the section renders empty with no fallback message. Low severity since the registry is a committed static file, but worth noting for future dynamic data loading.

## Taxonomy data integrity failure

The most consequential issue in this change is the species data. The fetch script (`scripts/fetch-species-data.js`) uses GBIF taxon keys from the registry to pull taxonomy, but the resulting JSON files contain wildly incorrect data:

- `african-elephant.json`: order Carnivora, family Felidae, genus Panthera, species Panthera onca (jaguar)
- `polar-bear.json`: family Felidae, species Panthera pardus (leopard)
- `hawksbill-turtle.json`: order Crocodylia, family Alligatoridae, species Caiman crocodilus (spectacled caiman)
- `tiger.json`: species Panthera leo (lion)
- `snow-leopard.json`: family Felidae, genus Puma, species Puma concolor (cougar)
- `orangutan.json`: family Cercopithecidae, species Cercopithecus roloway (a monkey)
- `amazon-river-dolphin.json`: family Balaenopteridae, species Balaenoptera physalus (fin whale)
- `coral-reef.json`: family Chiroteuthidae, genus Chiroteuthis (a squid)

Only `blue-whale.json` and `giant-panda.json` have plausible taxonomy. The root cause is likely that the GBIF API returned a different record than expected for the given taxon keys, or the script's response mapping is off. The `loadFallback()` function that reads back existing files means re-running the script won't fix this — it'll just reload the bad data as its own fallback. The taxonomy table is prominently displayed on every species profile page, so users will see "Family: Felidae" on an elephant page.

## innerHTML and data trust boundary

`species-page.js` builds HTML strings from JSON values and assigns them via `innerHTML` across six render functions (`renderTaxonomy`, `renderHabitat`, `renderMedia`, `renderThreats`, `renderConservation`, `renderCulturalSignificance`). Example from `renderMedia`:

```javascript
html += `<h4 class="media-card__title">${item.title || 'Unknown'}</h4>`;
```

If `item.title` contained `<script>alert(1)</script>`, it would execute. Today the JSON is static and committed, so an attacker would need repo write access. But the fetch script pulls from OMDb (movie titles) and GBIF (taxonomy strings) — both external data sources that could contain unexpected characters. A simple `escapeHtml()` utility applied to all interpolated values would close this gap without changing the rendering approach.

## Duplicate navigation elements on species pages

Each `species/*.html` file contains a hardcoded `<nav class="species-page__nav">` with a "Back to Observatory" link. The `species-page.js` module also calls `initNav()`, which creates and prepends a second `<nav class="site-nav">` element with breadcrumb. The user sees two navigation bars stacked at the top. Either the static HTML nav should be removed (letting `initNav()` handle it) or `initNav()` should detect the existing nav and skip insertion.

## Circular fallback pattern in fetch script

The fetch script's `loadFallback(id)` function reads `public/data/${id}.json` — the same file the script writes to at the end of processing. This creates a circular dependency: if the GBIF API is down or returns bad data, the script falls back to whatever was previously written. Since the committed files already contain incorrect taxonomy, running the script again without a valid API connection will preserve the errors. A cleaner pattern would be a separate `fallback/` directory with known-good seed data, or a validation step that checks `gbifData.species` against `species.scientificName` from the registry before accepting the response.
